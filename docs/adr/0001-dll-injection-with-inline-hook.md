# Runtime effect via DLL injection + an in-module loop, not an inline hook

APE needs to change existing game behavior (starting with crush-depth damage) at runtime. Considered a static binary patch to a target function's own bytes, an inline hook that replaces a target function via a trampoline (MinHook), and running APE's own logic in-process alongside the game while only reading/writing game memory (trainer-style, but in-process).

Chose **DLL injection plus an in-module loop that only reads and writes game memory** — APE does not hook, replace, or route through any stock SH3 function. `ape.act` is loaded via a dedicated `LoadLibrary` call site (ADR-0002); its `DllMain` spawns a background loop thread that resolves live values and applies effects by writing memory directly. This follows the convention experienced developers in this space learned the hard way: never patch, route through, or otherwise interact with stock SH3 functions — write your own that live alongside. It also proved *necessary* here: two RE sessions showed OAE has no crush-depth-specific function to hook (pressure damage is synthesized as a generic impact through the shared collision solver), so there was no clean inline-hook seam to take.

Consequences: MinHook is not used and has no current user in the suite — the "inline hook" half of the original decision is dropped. The `LoadLibrary` **injection** is retained. New hacks follow the same pattern: add a routine inside `ape.act` that reads/writes memory from the loop, rather than statically patching or inline-hooking a target function. Should a future hack genuinely require intercepting a function, inline hooking can be reconsidered then, as a deliberate exception to the alongside principle — not the default.
